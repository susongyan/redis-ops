# 业务 Key 拆分迁移与多 Key 命令支持方案

> 状态：阶段一实施中。后续阶段待实施，本文不代表当前运行版本已具备这些能力。
> 更新日期：2026-09-16。
> 架构提案：[ADR-025](adr/ADR-025-sync-command-semantics.md)。

## 1. 背景

历史上多个业务共用 Redis 集群，后续需要将某个业务迁移到独立 Redis。
目标不是屏蔽某类写入，而是持续复制指定业务 Key 的完整变化，包括新增、更新、删除和过期，
最终配合应用连接切换完成拆分。平台不自动切换业务连接或流量。

目前已有 Key 包含／排除匹配，以及代码定义的同步命令能力清单：

- `KeyFilter` 支持包含任一匹配、排除优先；包含为空时按全部 Key 处理。
- `CommandPlanner` 对部分单 Key 命令直接处理，对 MSET、DEL、UNLINK 提供拆分。
- 任务策略可以额外阻止命令、限制拆分及危险操作，但不能放开未知命令。
- RENAME、BITOP、集合存储运算、MULTI/EXEC 等目前仍在硬阻塞清单中。
- Console 的数据库命令目录只决定人工命令执行，不控制同步 Worker。

这套实现采取保守策略，但对真实业务拆分覆盖不足。需要从“多 Key 命令直接禁止”调整为
“按命令语义、过滤范围、目标拓扑判断”，同时保留 checkpoint、租约、generation 和 fence 的恢复约束。

### 行业方案参考

本次核对的 RedisShake v4 内置过滤器要求一条命令的 Key 全部通过；混合匹配时记录日志并丢弃整条，
Cluster Writer 要求命令所有 Key 同 Slot，否则停止。本项目借鉴 Key 元数据解析和通用发送，
不照搬混合范围整条丢弃，以免漏掉范围内数据。RedisShake v4 的恢复约束与本系统不同，不能直接替换执行器。

- [RedisShake 过滤规则](https://tair-opensource.github.io/RedisShake/en/filter/filter.html)
- [RedisShake Cluster Writer](https://github.com/tair-opensource/RedisShake/blob/v4/internal/writer/redis_cluster_writer.go)
- [RedisShake 当前限制](https://github.com/tair-opensource/RedisShake#limitations)

## 2. 目标、非目标与默认选择

### 目标

1. 以显式业务 Key 包含规则为主、排除规则为辅，保持全量与增量选择范围一致。
2. 在语义成立的情况下支持常见多 Key 命令，不因“多 Key”属性一律拒绝。
3. 支持复制流中的事务和 Lua effects，而不是在目标重新执行业务脚本原文。
4. 过滤或执行条件不成立时显示具体阻塞原因，不静默丢失范围内数据。
5. 明确区分“复制进度追平”和“数据校验通过”；不将校验当作放宽同步正确性的依据。

### 非目标

- 不新增任意命令数据库放行、未知命令透传、按命令跳过后继续的宽松模式。
- 不支持原文 EVAL/EVALSHA 重放、任意 Module 命令、动态 Key 模式 SORT 的通用适配。
- 不实现分布式跨 Slot 原子事务，也不自动转换跨业务边界的 RENAME、搬移等操作。
- 不支持运行中热修改过滤范围，不自动修补历史漏同步数据，不自动切流。

### 默认选择

- 包含为空仍表示全部 Key，但创建时必须明确确认；排除规则优先。
- 新任务保存不可变的 Key 规则和命令策略版本；扩大范围需要重新建立全量基线。
- 旧任务保留旧策略，不因升级 Worker 静默扩大支持范围。
- 首轮集成验收覆盖 Redis 6.2、7.x；其他版本不得仅凭命令名相同就声明兼容。
- 同步阶段目标业务范围应保持独占写入，切换前完成增量追平和范围内校验。

## 3. 命令语义与过滤决策

### 3.1 Worker 自有语义注册表

将命令名集合扩展为版本化描述和处理器：参数／子命令结构、Key 提取方式、读 Key、写 Key、
状态依赖、拆分能力、同 Slot 要求、目标版本要求。

不能统一将第一个参数视为 Key：BITOP、XGROUP、带 Key 数量的命令需要专门解析。
语义描述及执行适配归 Worker；sync-contract 只保留能力描述和策略版本等纯 Java 契约，
Platform 展示能力并做任务预检查，不拥有 Worker 的命令处理器。

### 3.2 统一规则

| 条件 | 行为 |
| --- | --- |
| 相关 Key 全在范围内，目标单机 | 已适配且版本兼容的命令原样执行 |
| 相关 Key 全在范围内，目标 Cluster 同 Slot | 原样执行 |
| 已识别命令所有写 Key 都在范围外，且无全局副作用 | 跳过 |
| 范围内结果依赖范围外输入 | 阻塞：输入依赖不完整 |
| 同时修改范围内外 Key | 除明确允许拆分的命令外阻塞 |
| Cluster 跨 Slot | 除明确允许拆分的命令外阻塞 |
| 参数、Key 或语义不明确 | 阻塞，不猜测 |

全局命令、协议控制命令、函数管理命令不套用“没有范围内写 Key 就跳过”的规则，保持专门处理。
保留内部命名空间保护；业务命令不得触达平台 checkpoint、fence 等内部 Key。

### 3.3 首批命令

| 类别 | 命令 | 范围与原子性处理 |
| --- | --- | --- |
| 独立多 Key | DEL、UNLINK、MSET | 沿用显式拆分策略；提示不保留跨 Key 原子性 |
| 条件性写入 | MSETNX | 所有依赖及写 Key 必须在范围内，不拆分 |
| 重命名／搬移 | RENAME、RENAMENX、SMOVE、LMOVE、RPOPLPUSH | 相关依赖与写入范围完整；跨边界不转换 |
| 复制 | COPY | 解析源、目标及 DB 选项；本期跨 DB COPY 阻塞，不猜测目标 DB |
| 多输入单结果 | BITOP、SUNIONSTORE、SINTERSTORE、SDIFFSTORE、ZUNIONSTORE、ZINTERSTORE、ZDIFFSTORE、PFMERGE | 结果在范围内时输入必须全在范围内；结果在范围外且无其他写入可跳过 |

以上均受目标版本及 Cluster 同 Slot 限制。阻塞命令客户端调用在复制流中可能呈现为其他写命令，
必须用真实 Redis 确认传播形态，不直接将所有阻塞命令原文加入支持名单。

## 4. 事务、Lua 与执行恢复

### 4.1 复制事务组装

Redis 5 起默认复制脚本写入效果；Redis 7 不再支持脚本原文复制。效果命令通过事务形式传播。
见 [Redis 脚本复制说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)。

新增事务组装器，MULTI 到 EXEC 为一个不可拆分执行单元：

- 完整收到 EXEC 前不应用内部命令，成功 checkpoint 不进入事务中间。
- 所有业务 Key 在范围内时整体执行，所有业务写入在范围外时整体跳过。
- 混合范围事务本期阻塞，不过滤部分命令后声称保留了事务语义。
- Cluster 目标要求事务整体同 Slot，不按 Slot 拆成多个独立事务。
- 消费源端事务标记，目标由执行器重新包装，不嵌套发送 MULTI。
- 默认组装上限 10,000 条命令、16 MiB；读取及累计过程检查限制，超限失败关闭。
- 断流、暂停或接管只从完整提交边界恢复；未闭合事务不得当普通批次提交。

### 4.2 必须先修正“EXEC 成功”的判定

当前目标执行器将业务命令和 checkpoint SET 放在同一个 MULTI/EXEC 中。
Redis 运行期错误不会回滚其他命令，业务命令失败时 checkpoint SET 仍可能执行。
因此仅看到 checkpoint 已推进，不足以证明业务批次全部成功。
见 [Redis 事务错误语义](https://redis.io/docs/latest/develop/using-commands/transactions/)。

计划增加目标端持久化批次确认状态，作为扩展命令的前置条件：

1. 执行前保存待确认标记，含任务、epoch、generation、offset 范围及摘要，不含原始 Key/value。
2. 逐项检查 EXEC 回复；区分待确认执行位置和已确认成功位置。
3. 全部成功后，在 fence 保护下完成确认并清除待确认标记。
4. 运行错误、回复丢失或重启后发现未确认标记，阻塞为“执行结果待核实”；禁止盲目重放、
   自动忽略标记或仅凭执行位置继续。人工核实或显式重建，不自动清空目标。
5. Cluster 标记与对应 checkpoint、fence 同 Slot；全局已确认进度不能越过任何未确认分片。
6. 排队错误、EXECABORT、WATCH 冲突等可证明未执行的情况，必须有测试证据后才能安全重试。

待确认标记的精确写入顺序、旧 checkpoint 升级格式、接管及响应丢失处理，在阶段一形成独立状态转移表
并完成故障测试后冻结；不能将本文概述直接视为已证明的 exactly-once 协议。
Redis 部分写入不会被该机制回滚；它保证不把已知不确定状态静默当成功或重复执行。

## 5. 配置、API、界面及可观测性

- 保留任务包含／排除规则，增加纯浏览器示例匹配预览；示例不落库、不进入日志或审计。
- 新任务显式携带新版策略，旧策略继续旧行为；Worker 能力声明必须包含可处理的策略版本。
- 领取时校验能力，不支持该版本的 Worker 不执行；升级 Platform／Worker 的顺序纳入部署说明。
- 扩展现有能力查询与任务详情响应，展示支持、有条件支持、暂不支持及限制原因，
  不建立与 Console 共用的命令配置表。
- 统计已应用、Key 过滤、拆分、阻塞的数量，明确是源命令数还是目标操作数；事务单独计数。
- 原因使用固定错误码：范围外输入依赖、跨范围写入、跨 Slot、事务混合范围、事务容量超限、
  参数／版本不支持、执行结果待核实。
- 日志、metrics、审计和异步 payload 只记录命令名、固定原因、计数、任务 ID、offset 等，
  不携带 Key/value、脚本原文或完整命令参数。新增详情遵循现有审计边界。
- 数据校验需与迁移的 Key 范围一致；抽样、降级或不确定结果不能展示成全量一致性结论。

## 6. 分阶段实施与验收

每阶段实现、验证、审查后独立提交；阶段门槛未通过不进入下一阶段。

| 阶段 | 交付物 | 验收门槛 |
| --- | --- | --- |
| 一：能力与恢复基础 | 注册表、Key 角色解析、计划结果、批次确认状态机、协议版本及 ADR 定稿 | 运行错误、回复丢失、崩溃及接管不能造成未确认批次自动重放或成功跳过；暂不扩大放行范围 |
| 二：多 Key 与业务过滤 | 首批处理器、全量／增量规则一致性、单机及同 Slot 执行 | 逐命令完成范围内外组合、版本、参数、二进制 Key、跨 Slot 测试 |
| 三：事务与 Lua effects | 有界事务组装、整组过滤、事务执行及恢复 | 真实 Lua／MULTI 流测试；事务跨读取批次、超限和断流不发生半事务提交 |
| 四：页面与交付 | 规则预览、能力及阻塞展示、统计、升级和恢复手册 | 桌面／窄屏检查、Platform/Worker/contract 验证、前端构建及迁移回灌通过 |

资源及集成测试在隔离 Redis Standalone、Sentinel、Cluster 与 MySQL 中执行，不修改生产实例：

- 源端造数、全量阶段持续写入、增量追平、范围内最终数据及 TTL 校验。
- 所有 Key 在内、全部在外、部分匹配、范围外输入依赖、内部保留 Key。
- 同 Slot、跨 Slot、MOVED/ASK、主从切换与已有拓扑处理回归。
- 错误类型、参数不兼容、内存不足等目标执行失败；重点覆盖 EXEC 返回局部错误。
- 发送前、执行中、回复前、确认前后断线或杀进程；generation 变化及旧 Worker 延迟写入。
- 非幂等 INCR、列表搬移在恢复后不得盲目重复执行。
- 大事务和持续高吞吐下内存、spool、背压有界，不以取消容量限制换兼容性。
