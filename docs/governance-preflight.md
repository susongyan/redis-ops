# TTL / 数据清理：预检、暂停和直接执行

## 已实现流程

- 常规：新建 → 运行预检 → 待审批 → 审批 → 确认执行。
- 直接执行：新建 → **跳过预检并执行** → 填写原因、核对范围、勾选风险确认 → 提交正式执行。
- 预检暂停后：恢复预检继续只读扫描；或者 **跳过剩余预检并执行**，同样需要填写原因并明确确认。
- 正在预检不能直接跳过；先暂停，等正在执行的批次退出。若提示 `REQUEST_IN_PROGRESS`，稍后再试。
- 预检暂停使用 `DRY_RUN_PAUSED`，执行暂停仍是 `PAUSED`；普通 start 入口拒绝预检暂停状态。
- 详情统一为右侧抽屉，显示配置、授权状态、运行统计和分片游标；部分预检统计不代表全量结果。
- 列表只保留“详情”入口；预检、跳过预检并执行、审批、执行及暂停/取消均集中在详情抽屉底部。

## API

TTL 与清理各新增 `POST /api/v1/{ttl|cleanup}-governance-tasks/{id}/skip-dry-run-and-start`。
要求已登录、`Idempotency-Key`、`If-Match` 及请求体：

```json
{"reason":"CHG-123：已确认业务范围","confirmed":true}
```

原因必填，最多 500 字符；不要包含实际 Key、密码或业务数据。未明确确认、状态不允许、版本冲突或旧批次仍执行时拒绝提交。
跳过、授权、执行入队和审计处于同一事务；同一个幂等键重试不会再次提交执行 Job。
原 `pause` 同时支持预检与正式执行；原 `dry-run` 支持恢复 `DRY_RUN_PAUSED`。取消不允许凭部分结果继续执行。

## 执行及审计边界

正式执行从头扫描，使用独立运行记录，不继承预检游标或计数。暂停恢复预检则复用未完成预检记录。
页统计和游标同事务保存，已完成分片不会因为恢复再次从 0 扫描；SCAN 本身仍可能重复返回。
旧版本 Job 不允许更新新阶段。领取租约逐页续期；暂停是批次边界停止，不是 Redis 侧即时撤回。

跳过入口分别记录 `*_SKIP_DRY_RUN`、`*_EXECUTION_AUTHORIZED` 和 `*_START`。
常规创建、预检、审批、执行、暂停、取消也补充审计快照：任务、集群/DB、状态、版本、数值预算和规则 SHA-256；不记录原始规则或 Key。
审计仍采用服务端登录身份及账号/显示名快照。跳过原因进入请求指纹和审计，清理任务还保存在授权说明中；不进入异步 Job payload。

TTL 仍仅对无过期时间的 Key 做条件设置。清理仍使用 UNLINK。已产生的修改或删除不能通过暂停/取消回滚。
当前 TTL `maxKeys` 是匹配检查预算，不是独立的修改数量计数；不承诺 Redis 与 MySQL 跨系统 exactly-once。
本次没有将预检扫描改为轻量 TTL 专用扫描，原有查询开销仍存在。

## 发布

不涉及新表或 schema 变更，无需新增 DDL。新增状态使用原 VARCHAR 列；最新初始化 SQL 保持不变。
前后端一起发布；升级前停止旧版治理任务，等待执行退出，避免新旧 Job payload/执行器混跑。
旧版未携带任务版本的 Job 不自动推测版本执行；存量活跃任务需在旧版停止后重新发起。
