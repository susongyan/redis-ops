# ADR-037：数据库会话时区交由数据库自身决定

- 状态：已接受
- 日期：2026-11-02
- 关联契约：架构契约第 3 节；修订 [ADR-005](ADR-005-utc-persistence-time-semantics.md) 的连接条款

## 背景

ADR-005 要求 JDBC URL 固定 `serverTimezone=UTC`，假设数据库 `DATETIME(3)` 一律以 UTC 标签写入。
实际运行中数据库服务器与会话运行在本地时区（+08）：`CURRENT_TIMESTAMP` 默认值、心跳与租约的
SQL 端时间运算按 +08 壁钟执行，而应用经 UTC 会话读出时被驱动整体偏移，出现"读出的时间比写入
晚 8 小时"一类的双重转换错误（同步任务行的壁钟重整修复即源于此）。强制两种标签中的任何一种，
都会把"会话标签"与"数据库自身时区"耦合进每个部署模板。

## 决策

1. JDBC URL **不携带任何会话时区参数**（既不 `serverTimezone` 也不 `connectionTimeZone`）；
   会话时区由数据库服务器自身设置决定。
2. 共享 schema 的所有 `DATETIME` 列按**单一标签**——数据库会话壁钟——写入与读取：
   `CURRENT_TIMESTAMP` 默认值、租约/心跳的 SQL 端运算与 Java `Instant` 参数在同一会话标签下
   一致，读出时不做二次转换（见 `SyncMapper` 的约定注释）。
3. 应用与数据库的部署约定保持同一时区标签（当前部署为 +08）。同一套数据被不同时区标签的
   数据库会话读写属于不支持的拓扑。
4. ADR-005 的"应用层统一 `Instant` 语义"保留：API 与领域模型仍以 `Instant` 表达时间，
   页面按浏览器时区展示；被取代的仅是"JDBC URL 固定 `serverTimezone=UTC`"条款。

## 后果

- URL 模板与部署文档不再需要时区参数，消除会话/服务器标签不一致的一整类偏移缺陷。
- 混用不同数据库时区的部署会在读写间产生静默偏移；运维必须保证所有实例时区一致。
- 任何新服务、脚本或 BI 查询连接该库时，必须接受同一约定：按会话壁钟原样读 `DATETIME`。

## 落地与验证

Platform 与 Worker 的 `application*.yml` URL 模板已去除时区参数；`SyncMapper` 等持久层注释
指向本 ADR。部署文档示例同步更新。
